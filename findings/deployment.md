# Deployment field guide

This guide is part of a library of digital takeaways and examples that support Productside's teaching and advisory services on the Agentic Development Lifecycle (ADLC).

## What this phase is for

Deployment is where an agent that passed evaluation becomes something real users and real systems depend on. The decision it supports is simple to state and hard to make: should this specific version of the agent, with these permissions, on this infrastructure, at this cost, be exposed to this audience now, and how will we undo it if we are wrong?

For agents, the unit being released is wider than a model. A release bundles prompts, tool definitions, configuration, memory settings, retrieval indexes and permissions, any of which can change behavior ([Microsoft, GenAIOps](https://learn.microsoft.com/en-us/azure/architecture/ai-ml/guide/genaiops-for-mlops); [IBM, Agent Lifecycle Management](https://www.ibm.com/think/topics/agent-lifecycle-management)). This guide covers release, rollout, environments, versioning, cost and reliability. Governance, evaluation design and observability have their own guides and appear here only where they decide whether a release goes ahead.

## What the sources agree on

1. **Release the whole agent as a versioned unit, and keep every version retrievable.** Prompts, tools, configuration and index changes should each produce an identifiable version with a release record. Immutable versions are what make comparison and rollback possible. Label: Fact (as described by several platform vendors), Inference that the habit applies on any platform. See [AWS, AgentCore Runtime](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/runtime-how-it-works.html), [Microsoft, Foundry lifecycle](https://learn.microsoft.com/en-us/azure/foundry/agents/concepts/development-lifecycle), [AWS, AgentOps](https://aws.amazon.com/blogs/machine-learning/agentops-operationalize-agentic-ai-at-scale-with-amazon-bedrock-agentcore/), [Google SRE, Release Engineering](https://sre.google/sre-book/release-engineering/).

2. **Promote through separate environments, with approval before production.** At least development, test and production, with access restricted per environment, configuration and secrets scoped to each, and the same tested revision moved forward rather than rebuilt. Some settings do not travel with a package (authentication, sharing, monitoring) and need a manual check after every promotion. Fact (vendor guidance). See [Microsoft, ALM for Copilot Studio](https://learn.microsoft.com/en-us/microsoft-copilot-studio/guidance/alm), [Microsoft, promoting hosted agents](https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/deploy-hosted-agent-production), [SAP, Joule Studio](https://architecture.learning.sap.com/docs/ref-arch/f5a3ef).

3. **Roll out gradually, and make rollback a routing change.** Sandbox, then canary, then full traffic is the common pattern; blue-green and rolling variants appear too. Keep the stable version live until the candidate is accepted. Fact as description of practice, not evidence of effectiveness. See [IBM, ADLC](https://www.ibm.com/think/topics/agent-development-lifecycle-adlc), [Google Cloud, production-ready agents](https://cloud.google.com/blog/products/ai-machine-learning/a-devs-guide-to-production-ready-ai-agents), [Anthropic, multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system) (which describes "rainbow" deployments so running agents are not interrupted).

4. **An evaluation result should be able to stop a release.** Several sources describe thresholds in the delivery pipeline that block a change, with a baseline from a known-good version. Because judge scores vary between runs, thresholds need margin, and a faster subset can run on each change. Fact for the mechanism; the benefit is vendor-asserted. See [AWS, evaluation with GitHub Actions](https://aws.amazon.com/blogs/machine-learning/automated-agent-evaluation-with-amazon-bedrock-agentcore-and-github-actions/), [Braintrust, testing agents](https://www.braintrust.dev/articles/how-to-test-ai-agents), [Google Cloud, quality gate](https://cloud.google.com/blog/topics/developers-practitioners/a-methodical-approach-to-agent-evaluation), [Microsoft, observability](https://learn.microsoft.com/en-us/azure/foundry/concepts/observability).

5. **Permissions and secrets are deployment decisions.** Give each agent its own identity, grant least privilege, require human approval for irreversible actions, and keep credentials outside the agent's reach, typically behind a proxy. Fact (multiple sources, including government guidance). See [Anthropic, securely deploying agents](https://platform.claude.com/docs/en/agent-sdk/secure-deployment), [LangChain, going to production](https://docs.langchain.com/oss/python/deepagents/going-to-production), [ACSC and partners](https://www.cyber.gov.au/business-government/secure-design/artificial-intelligence/careful-adoption-of-agentic-ai-services), [Singapore IMDA](https://www.imda.gov.sg/-/media/imda/files/about/emerging-tech-and-research/artificial-intelligence/mgf-for-agentic-ai.pdf), [A2A enterprise guidance](https://a2a-protocol.org/latest/topics/enterprise-ready/), [MCP security](https://modelcontextprotocol.io/docs/2026-07-28/tutorials/security/security_best_practices).

6. **Hosting an agent is not hosting a stateless service.** Sessions hold state, run long, and can be lost on restart. Teams must decide what persists, how runs resume after failure, and how sandboxes are isolated and cleaned up. Fact (vendor documentation). See [Anthropic, hosting](https://platform.claude.com/docs/en/agent-sdk/hosting), [Anthropic, managed agents](https://anthropic.com/engineering/managed-agents), [LangChain, durable execution](https://docs.langchain.com/oss/python/langgraph/durable-execution), [Microsoft, durable workflows](https://devblogs.microsoft.com/dotnet/durable-workflows-in-microsoft-agent-framework/), [Pydantic, durable execution](https://pydantic.dev/articles/pydantic-ai-dbos).

7. **Cost is a design property, driven mostly by model usage.** Token consumption, number of turns, model choice and standing context dominate; hosting infrastructure is usually smaller. Anthropic reports agents use about four times the tokens of chat and multi-agent setups about fifteen times (vendor data). Set budgets per successful task and route to the smallest capable model. See [Microsoft, choice of agent host](https://learn.microsoft.com/en-us/agents/architecture/host-platform), [Product School, deployment checklist](https://productschool.com/blog/artificial-intelligence/ai-agent-deployment), [Uddin, shipping agents](https://dev.to/tamizuddin/from-hype-to-hard-reality-what-were-learning-about-shipping-ai-agents-in-production-42il), [Kapoor et al., AI Agents That Matter](https://arxiv.org/abs/2407.01502) (peer-reviewed-or-preprint; accuracy reported without cost misleads).

8. **Reliability compounds against you.** A ten-step task at 85 percent per-step accuracy succeeds roughly one time in five. Fact as arithmetic, with the 85 percent illustrative. Hence bounded scope, idempotent tool actions, timeouts and circuit breakers on loops. See [The AI Engineer, why agents fail](https://theaiengineer.substack.com/p/why-ai-agents-keep-failing-in-production), [Product School](https://productschool.com/blog/artificial-intelligence/ai-agent-deployment), [Mind the Product](https://www.mindtheproduct.com/product-management-for-agentic-ai-when-to-build-agents-and-wow-to-do-it-well/).

9. **Deployment leads into operation, not an end state.** Monitoring, feedback and re-evaluation after launch are part of the same phase boundary. See [Microsoft, agent development lifecycle](https://learn.microsoft.com/en-us/agents/architecture/deployment-lifecycle), [Evaluation-Driven Development and Operations (EDDOps)](https://arxiv.org/abs/2411.13768), [IBM, deploying agents](https://www.ibm.com/think/topics/ai-agent-deployment).

10. **Shipping speed and stability are not necessarily a trade.** DORA's research reports they usually move together, and gives five delivery measures: change lead time, deployment frequency, failed deployment recovery time, change fail rate and deployment rework rate. Fact as research finding, strong but not universal; DORA warns against turning the numbers into targets. Whether the measures transfer unchanged to agent releases is Unknown. See [DORA metrics](https://dora.dev/guides/dora-metrics/).

## Where they disagree or differ

- **Vocabulary.** The same ideas carry different names: "deploy and provision" (IBM), "release and monitor" (Databricks), "publish" (Microsoft Foundry), "operational steady state" (Microsoft), a "Deploy" mode that runs concurrently with others (adlc.io). Compare [Databricks](https://learn.microsoft.com/en-us/azure/databricks/agents/agents-dev-lifecycle) and [adlc.io](https://www.adlc.io/). Treat the labels as local; match on the activity.
- **Platform slant.** Each cloud vendor describes safe release in terms of its own runtime, endpoints or packaging ([AWS](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/runtime-how-it-works.html), [Google ADK](https://google.github.io/adk-docs/deploy/), [Google Agent Engine](https://cloud.google.com/vertex-ai/generative-ai/docs/agent-engine/overview), [Microsoft](https://learn.microsoft.com/en-us/agents/architecture/host-platform)). Managed hosting is framed as less work; self-hosting as more control. None offers a neutral cost comparison.
- **Autonomy appetite.** Practitioners and government guidance push staged autonomy and human gates ([Mind the Product](https://www.mindtheproduct.com/product-management-for-agentic-ai-when-to-build-agents-and-wow-to-do-it-well/), [IMDA](https://www.imda.gov.sg/-/media/imda/files/about/emerging-tech-and-research/artificial-intelligence/mgf-for-agentic-ai.pdf)). Others are more optimistic: the adlc.io manifesto favors loops over gates, and Google's CLI announcement claims weeks-to-hours delivery without data ([Google Developers, Agents CLI](https://developers.googleblog.com/agents-cli-in-agent-platform-create-to-production-in-one-cli/)).
- **Where to enforce control.** Some sources favor a central control plane or shared platform ([IBM, control plane](https://www.ibm.com/think/topics/agent-control-plane), [BCG](https://www.bcg.com/publications/2026/the-four-pillars-cios-can-use-to-scale-agentic-ai), [PwC](https://www.pwc.com/us/en/about-us/newsroom/press-releases/pwc-launches-ai-agent-operating-system-enterprises.html)); the workflow-first vendors keep control inside the application ([CrewAI](https://docs.crewai.com/en/concepts/production-architecture)). These are not exclusive, but they imply different ownership.
- **Evidence strength.** Consultancies and vendors report large gains and fast scale (for example [EY](https://www.ey.com/en_gl/insights/ai/building-an-enterprise-scale-agentic-ai-operating-system), [Salesforce](https://www.salesforce.com/news/press-releases/2024/11/20/agentforce-testing-center-announcement/)); these are self-reported and promotional. Government and standards sources state obligations but not outcomes.
- **Canary on agents.** Several sources borrow canary and blue-green from conventional software. Government guidance notes that agent-specific evaluation methods are immature and agents may behave differently when they detect testing ([ACSC](https://www.cyber.gov.au/business-government/secure-design/artificial-intelligence/careful-adoption-of-agentic-ai-services)), which weakens the assumption that a small pilot predicts full-scale behavior.

## What to do in this phase

1. **Confirm readiness against the evaluation record.** Product owner, engineering and an independent reviewer check that agreed thresholds were met on the exact version being released. Evidence: evaluation report tied to the version identifier, known limits in business terms ([Databricks](https://learn.microsoft.com/en-us/azure/databricks/agents/agents-dev-lifecycle)).
2. **Decide the permission and autonomy level.** Product, security and the business owner choose among suggest, act with approval, and act alone, per action type ([Mind the Product](https://www.mindtheproduct.com/product-management-for-agentic-ai-when-to-build-agents-and-wow-to-do-it-well/)). Evidence: a permission matrix and a list of irreversible actions with their gates. If the use is regulated, name the oversight owners and log retention duties ([EU AI Act Art. 26](https://ai-act-service-desk.ec.europa.eu/en/ai-act/article-26), [UK code of practice](https://www.gov.uk/government/publications/ai-cyber-security-code-of-practice/code-of-practice-for-the-cyber-security-of-ai)).
3. **Choose the host and set the cost envelope.** Platform, engineering and finance decide managed versus self-hosted, state persistence, isolation level and a budget per successful task. Evidence: cost estimate from real traces, not demos ([Product Talk](https://www.producttalk.org/customer-interview-coach/) reports per-item cost varying by an order of magnitude).
4. **Prepare environments and the release path.** Engineering sets up development, test and production, scopes secrets, and lists the settings that need manual checks. Evidence: promotion checklist and environment map.
5. **Dress rehearsal in a safe environment.** Run representative and adversarial scenarios where real actions are stubbed or isolated ([UK AISI, sandboxing](https://www.aisi.gov.uk/blog/the-inspect-sandboxing-toolkit-scalable-and-secure-ai-agent-evaluations)). Evidence: run logs and failures turned into permanent test cases.
6. **Staged exposure.** Internal users, then a small share of traffic, then widening steps, with a named person authorized to pause. Evidence: per-stage metrics against pre-set stop conditions.
7. **Rehearse rollback and shutdown.** Prove that rollback restores the prior version, that a kill switch works, and that in-flight sessions behave sensibly. Evidence: a timed rollback drill.
8. **Hand over to operations.** Register the agent with owner, version, environments and runbook. Retirement planning starts here: versions of agents tend to coexist until someone removes them, so record dependents now (Inference).

## Artifacts this phase should produce

| Artifact | Purpose | Minimum contents |
|---|---|---|
| Release record | Make each release traceable and reversible | Version identifiers for prompts, tools, configuration, index; evaluation results; approver; date; rollback target |
| Go or no-go memo | Document the release decision | Thresholds, results, known limits, residual risks, sign-offs |
| Permission and autonomy matrix | Show what the agent may do alone | Actions by tier (read, write, irreversible), gates, identity, credential handling |
| Rollout plan | Control exposure | Stages, traffic shares, stop conditions, pause authority, communication to users |
| Rollback and kill-switch runbook | Limit damage quickly | Triggers, steps, owner, drill result |
| Cost and capacity model | Prevent budget surprise | Cost per successful task, token and concurrency assumptions, caps |
| Agent registry entry | Hand-off to operations | Owner, version, environments, dependents, support contact |

## Questions a product leader should ask

1. Which exact version is being released, and where is the evidence it was evaluated?
2. What counts as a failed release, and who can stop it without asking permission?
3. If we roll back today, what returns to its prior state and what does not (memory, indexes, sessions, completed actions)?
4. Which actions can the agent take that cannot be undone, and who approves each?
5. Whose identity does the agent act under, and could it exceed the rights of the user it serves?
6. What is our cost per successful task at expected volume, and what happens when usage doubles?
7. What breaks if the model, a tool schema or a credential changes underneath us?
8. How did the test environment differ from production, and what was never tested?
9. How will a failure in production become a new test case?
10. Who is on call for this agent, and have they seen a trace of a bad run?
11. Which settings are manual after promotion, and who verifies them?
12. Who knows this agent exists, and who depends on it?

## Failure modes

- **Demo-to-production jump.** The pilot works in a chat tool, then fails on security, sharing or cost. Early sign: no one can state the production permission model ([Product Talk](https://www.producttalk.org/customer-interview-coach/)).
- **Unversioned changes.** Someone edits a prompt live. Early sign: the team cannot say what changed between Tuesday and Friday.
- **Environment in name only.** Test and production share resources or credentials. Early sign: a test run touches live data ([Microsoft](https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/deploy-hosted-agent-production)).
- **Silent guardrail weakening.** Agent-level settings replace model-level ones. Early sign: no one has tested the effective policy after publishing ([Microsoft, guardrails](https://learn.microsoft.com/en-us/azure/foundry/guardrails/guardrails-overview)).
- **Credentials inside the sandbox.** Early sign: secrets readable by the agent's own tools ([Anthropic, managed agents](https://anthropic.com/engineering/managed-agents)).
- **State lost on restart.** Early sign: long tasks restart from zero after a redeploy.
- **Runaway cost.** Retries and loops multiply spend. Early sign: cost per task is unknown or rising without a cause.
- **Parallel work beyond review capacity.** Output outpaces human review ([Pragmatic Engineer](https://newsletter.pragmaticengineer.com/p/new-trend-programming-by-kicking)). Early sign: growing queue of unreviewed changes.
- **Metrics as targets.** Early sign: teams optimize deployment frequency while rework rises ([DORA](https://dora.dev/guides/dora-metrics/)).

## Gaps in the evidence

The corpus is large for this phase (dozens of sources) but uneven in quality. Most of it is vendor documentation describing intended practice. There is little independent evidence that canary releases, evaluation gates or durable execution improve outcomes for agents; treat those as Inference drawn from conventional software and ML operations. The classic delivery research (DORA, SRE) predates agents, so its transfer is a Hypothesis. Cost figures are vendor-reported and workload-specific. Survey and forecast numbers quoted by sources (failure rates, adoption shares, speedups) were not checked and should be treated as Unknown. The corpus says little about incident case studies with named postmortems, about multi-region reliability, about contract and service-level terms with model providers, about version pinning against provider model deprecations, and about the cost of human review at scale. Several sources are undated, so recency is uncertain. No license was verified for most sources; two Google Cloud pages state CC BY 4.0 and the UK code states the Open Government Licence.
